# 上架主流程（temu-bot run）

一行商品从表格走向店小秘的全过程。代码在 `src/temu_bot/listing.py`。

## 先决条件：表格 + 它指出的图片位置

上架只需要给**信息表格**（配置里的 `project.table`）。图片位置**由表里给**：

- 第 1 列「文件夹路径」= 图片放在哪个目录
- 各图片列（主图 / 素材图…）= 文件名

**表里写的是名字，不是图片本身** → 所以要拿名字去表里指的那个目录**找**。
这一步由 `preflight` 和 `MEDIA` 步负责，任何一行找不到图，都会在**碰接口之前**被挡下来。

```bat
temu-bot preflight                      :: 只读，验表格与它指向的图片
```

> `--images-dir` 是个可选覆盖项（表里路径写错/临时换一批图时用得到），
> 平时不需要给。

「找」不是死拼路径——表里的名字是人手填的，实际文件名常被改过。按可靠度依次尝试，
**只要不唯一就不猜**（猜错就是给商品配错图）：

| 方式 | 场景 |
|---|---|
| `exact` | 完全一致（**大小写也要一致**，不依赖操作系统的宽容度） |
| `casefold` | 只有大小写不同 |
| `stem` | 扩展名不同（表里 `.jpg`，文件夹里 `.png`） |
| `recurse` | 图被放进了子文件夹 |
| `prefix` | 唯一的前缀匹配（表里 `123.jpg`，文件夹里 `123-素材图.jpg`） |
| `ambiguous` | 匹配到多张 → **报错，不猜** |

## 步骤

| 步骤 | 读写 | 做什么 | 失败会怎样 |
|---|---|---|---|
| `PRECHECK` | 只读磁盘 | 表格列的齐不齐：有文件夹？有主图？**有素材图**？有模板 SPU？有中文标题？ | 停，**一次接口都不发** |
| `MEDIA` | 本地写 `work/` | 按表里的名字**去图片文件夹找图**，再按 Temu 规格出图（见 `docs/图片管线.md`）。**原图只读** | 停，别等平台打回 |
| `SHOP_CHECK` | 只读接口 | **核对店铺**（见下） | 停，绝不复制 |
| `FIND_TEMPLATE` | 只读接口 | 用模板 SPU 在 在线→待发布 里搜出模板商品 | 停；若搜不到，多半是登错账号 |
| `COPY` | **写** | `POST /api/banjia/copyProduct.json` 复制模板 → 进待发布 | 停 |
| `FIND_NEW` | 只读接口 | 在待发布列表里找刚复制出来的新商品 id | 停（原工具也专门处理过这个坑） |
| `UPLOAD` | **写（占图片空间）** | 把 `MEDIA` 出好的图传到店小秘（见 `docs/图片上传.md`） | 停，别存下去 |
| `APPLY` | **写** | 读商品 → **换主图**（展示图保留）+ **填 SKU 货号** + 改中英文标题 → `save_product(op)` | 停 |
| `VERIFY` | 只读接口 | **仅 op=2**：提交后回读商品详情，看店小秘到底发布成功没有（`publishFail` / `errMsg`） | 判失败 → 状态写「失败」+ 原因 |
| `WRITEBACK` | **写表格** | 把商品ID / 状态 / 问题项写回表格（见下） | 上架结果**不受影响**，但要补写 |

> `PRECHECK` 要求**素材图也在**：缺素材图时素材图位会留着模板那张，上出来是个
> "半对"的商品。收集图片那一步本来就把这种行跳过了，所以这里也照同一条规矩挡。

`UPLOAD` 与 `APPLY` 是一体的：图**必须**在保存之前写进商品对象，否则存下去的
仍旧是模板的图——那正是"标题对、图片是模板的"错商品的由来。所以：

- 换图**一处都没写进商品字段**时，`APPLY` 直接 `FAIL` **中止**，绝不保存。
- 干跑时 `UPLOAD` 只报告"会传哪几张"，一张都不传。

## 店铺核对（最重要的一条）

你的规矩：**上架时你人工切换店铺，工具负责核对，不一致就停下提醒**。
2026-10-16 又补了一条：**「我们登录，程序核对确认即可」**——所以**不用你手选登录身份**。

**店铺不固定、会随情况变化**，所以这里：

> **不看配置里的静态映射。** 配置（`config.shops`）随时可能过期，只当提示。
> 一律以**实时读到的登录账号店铺列表**（`userIn.shopMap`）为准。

`SHOP_CHECK` 做两件事：

1. **认身份**：拿表里第 10 列的店铺名，挨个问"这个登录身份的账号里有没有这家店"，
   谁有就是谁。**每次都实时问、不缓存**——用户切店/重新登录后下一行立刻生效。
2. **拿 shopId**：用认出来的那个身份再确认一遍，并把 `shopId` 交给后面几步
   （复制就是打在这个 shopId 上的）。

| 情况 | 结果 |
|---|---|
| 某个身份的账号里有这家店 | 通过，用那个身份继续 |
| 谁都没有 | **停**，并说清查过哪些身份、它们账号里实际有哪些店 |

```
✅ SHOP_CHECK：表里「SWEET SHIRT SHOP」↔ 登录身份「hat-tshirt」（自动认出来的）
              ↔ 账号里的店「SWEET SHIRT SHOP」(shopId=8665618)

❌ SHOP_CHECK：表里要上「XXX」，但**没有任何登录身份的账号里有这家店**。
   查过的身份：hat-tshirt（账号里没有这家店）；lovely（没登录 / 登录态过期）。
   这些账号里见到过的店：A hat tshirt、A lovely costume。
```

CLI 上仍可以 `--shop <身份>` 手动指定（排查时用），不指定就是自动认。

> 账号的 `shopMap` 里除了真店铺还有内部占位桶（实测见过「手工订单」，id 是 0），
> 提示里会滤掉，免得添乱。

### 模板也必须在**这家店**里

`FIND_TEMPLATE` 用第 11 列的 SPU 去搜，**搜索限定在核对出来的那个 `shopId`**，
搜到之后再拿商品自己的 `shopId` 复核一遍。找不到就停：

```
❌ FIND_TEMPLATE：在「A hat tshirt」(shopId=9013981) 里**找不到**模板 SPU 9082676134
   （在线的、待发布的都搜过了）。→ 请确认：① 这个 SPU 确实是这家店的商品；
   ② 表里第 11 列模板 SPU 有没有写错。
```

复核那一步是防"过滤参数没生效"：账号里有多家店、同一个 SPU 在别家店也有的话，
不校验就会把**别家店的商品**当成模板复制，复制出来完全不相干。

这两个 ❌ 都会在网页控制台顶部**单独弹一条横幅**点名，不用去结果卡片里翻。

> 曾经踩过的两个坑：① 拿"登录配置自己的期望店铺"去核对——那是自证，永远过；
> ② 拿配置里"这家店该用哪个登录身份"去比——店铺一变或没登记就误判。
> 现在两条都换掉了，有测试钉住（`tests/test_listing.py`）。

## 干跑 vs 真实

**默认干跑**（不加 `--live`）：

- `COPY` / `APPLY` 一步都不发。`COPY` 只把**将要发出去的载荷**打出来。
- 但 `APPLY` 会**只读地**读一次模板商品，把标题的真实 before→after 算给你看：

```
🔸 APPLY：（干跑，以模板为样本）中文标题 '长袖T恤女装猫咪小睡趣味印花圆领休闲'
   → '男士短袖圆领T恤猫咪印花夏季休闲'；英文标题 "Women's Long Sleeve T-Shirt Cat
   Nap Funny Prin" → "Men's Short Sleeve Round Neck T-Shirt Cat Prin"（op=1）
```

真实执行要显式加 `--live`。那一步会**真建出商品**、**真写数据**、**真往图片空间传图**，
必须单独批准。

> 「复制扣米豆」**是个错误假设，已按实测改掉**：连续复制 6 次，`balanceView` 的
> `availableBalance`、`todayFreeBalance`、各服务 `availableCount` 一个都没变。
> 真正要防的是**重复铺货**——见下面「跑完要写回商品ID」。

`--op`：`1`=仅保存 / `2`=立即发布 / `3`=移入待发布。
**CLI 不写 `--op` 就是 `1`（仅保存）**；**控制台的「保存后的动作」默认是 `2`（立即发布）**
（用户 2026-10-16 要求）。两边默认不同是有意的：命令行保守，页面按用户习惯。

> `op=2/3` 时那一步**本身就是动作**，所以即使标题、货号、图片都没变也会提交出去
> （`listing.py` 里只有 `op=1` 才会"没什么可做就跳过"）。

## SKU 货号：用表里的，不用模板的

上架时把**表里第 9 列「一键生成SKU货号前缀编码」**填进商品，**不沿用模板的货号**
（模板的货号会让一批商品全挂同一个号）。

填的位置（对着老工具上架成功的 98 个商品核过，就是这么填的）：

| 位置 | 字段 | 填什么 |
|---|---|---|
| **SKU 级** | `variationListStr[*].extCode` / `variations[*].extCode` | 表里第 9 列的值（**所有尺码填同一个**） |
| **SKC 级** | `mainProductSkuSpecReqs[*].extCode` | **不动**，保留模板自己的（老工具也没动） |

第 9 列没有值 → `PRECHECK` 直接失败：那只能用模板的货号，正是用户不要的。

## 图片怎么换（**只换主图，展示图保留**）

规矩是用户 2026-10-16 定的，细节见 `docs/图片上传.md`：

```
模板：[主图A, 展示1, 展示2, 展示3, 展示4]
        ↓
结果：[新主图, 展示1, 展示2, 展示3, 展示4]
```

- 模板的**主图删掉**，表里那行的主图**顶到第 1 位**；
- 模板的**其它展示图原样保留**（要从**模板**读，不是从商品自己身上读）；
- SKU 缩略图跟着换成新主图；
- **颜色/尺码一个字都不动**。

## 换不换图：`--swap-images`

`UPLOAD` 默认按行**自动判断**：

| 这行的情况 | 默认行为 |
|---|---|
| 表里**没有**商品ID（新行） | 换图：把表里这几张图传上去，顶掉模板的主图 |
| 表里**已有**商品ID（第 32 行那种） | **不换**：这是给它"重试 / 续跑"，重复传图只会白占图片空间 |

已有商品ID 的行如果确实需要换图（比如上一版传错了），加 `--swap-images` 强制换。
强制也会**跳过复制**——已有商品的行永远不复制（那是重复铺货）。

## 命令

```bat
:: 上架前：验表格 + 图片文件夹（只读）
temu-bot preflight

:: 干跑表里第 32 行（不写任何数据）——登录身份不用给，程序按表里的店铺名自己认
temu-bot run --row-index 32

:: 图片文件夹不在表里第 1 列所指的地方时，显式指定
temu-bot run --row-index 32 --images-dir "D:\新图"

:: 真实跑（谨慎；确认过干跑输出再执行）
temu-bot run --row-index 32 --live --op 1

:: 已有商品ID 的行也强制换图
temu-bot run --row-index 32 --live --op 1 --swap-images

:: 排查时才手动钉死身份（平时不用）
temu-bot run --shop lovely --row-index 32
```

给用户的双击入口：

- `0-上架前检查.bat` —— 验「信息表格 + 图片文件夹」
- `1-登录店小秘.bat` —— 登录（控制台点「开始」也会在没登录态时自动打开登录窗口）
- `7-干跑上架一行.bat` —— 输入行号（登录身份留空就是自动认），跑一次干跑
- `8-检查图片并出图.bat` —— 看图片规格并出图

## 同一个商品 id 的两条路

表里第 13 列「商品ID」决定走哪条：

- **空** → 正常路：复制模板 → 找新商品 → 传图换图 → 改标题 → 保存
- **有值** → 续跑路：**跳过复制**（再复制就是重复铺货），直接在那个商品上改/发布

第 32 行就是后者（商品 `184807703165779045` 已建好、标题正确、图也合规，只差发布）。

## `WRITEBACK`：跑完把商品ID/状态写回表格（**流程里的一步**）

**跑一行就锁一行**，不等整批跑完——中断了也已经记下做过的。写三个格子：

| 列 | 写什么 |
|---|---|
| 13 商品ID | 跑出来的商品ID。**没拿到就不写**，绝不拿别的东西顶上 |
| 14 状态 | `成功` / `处理中` / `失败`（文案可在 `config.yaml` 的 `sheet.statuses` 改） |
| 16 问题项 | 失败时写第一条失败原因（`[步骤名] 说明`）；否则**清空** |

**`处理中` 是什么**：`op=2 立即发布` 时，店小秘保存接口返回 `code=0` 只代表
"存进店小秘了"，它还要异步推给 Temu。`VERIFY` 会立即回读一次，没定论就写
`处理中`；**整批跑完后再统一复核一次**，确认上线改成 `成功`、`publishFail`
改成 `失败` 并写原因。这样就不会再出现"表格写成功、店小秘里其实发布失败"。

**实测教训（2026-10-18）**：84 个商品全部保存成功，但店小秘推 Temu 时
`access_token is expired`，84 个全变 `publishFail`；当时没有 `VERIFY`，
表格全写成"成功"。补上回读后，这类问题会当场写进第 14/16 列。

**为什么非写不可**：表格里没有商品ID 的行，在流水线眼里就是"新建"。同一行再跑一次
会**再复制一遍模板、再建一个重复商品**——重复铺货是会被平台处罚的。
（复制本身不扣米豆；真正危险的是重复铺货。）

失败的行**也写**（状态=失败 + 问题项）：不然表里一直空着，下次还当"新建"跑。
还没动写操作就被取消的行**不写**——那一行什么都没发生。

### 表开着 Excel 的时候

回写会**被安全闸挡下**，但这**不会让上架结果作废**——商品已经建好了，抹掉只会更糟。
所以：

- `WRITEBACK` 那一步显示 ❌，并给出补写命令；
- **`outcome.failed` 保持"上架成功"**（否则会诱使你去重跑，那正好造成重复铺货）；
- 关掉表之后补上：

```bat
temu-bot table writeback                      :: 干跑，只报告将要写什么
temu-bot table writeback --live               :: 真写（先备份，落盘是原子替换）
temu-bot table writeback --from <日志> --status 成功
```

### 安全约定（`sheet/guard.py`）

- 写前先确认表**没被 Excel/WPS 打开**（`~$` 锁文件 + 独占打开试探），开着就拒绝、绝不硬写；
- 写前**先备份**到 `data/backups/`（保留最近 N 份；文件名带毫秒，批量跑不会互相覆盖）；
  批量跑时**一整批只备份一次**（那份"跑之前"的状态才是最该留的）；
- 只改指定的那几个格子，落盘走「同目录临时文件 + `os.replace`」原子替换；
- 表里那个格子**已经有别的商品ID**、且与这次的不一样时**拒绝覆盖**，让你人工确认。
